01

Start with the data

N is the number of coefficients in one polynomial, here 65,536. A tower stores those N coefficients reduced modulo one prime q, at slots 0 through N−1. Each stored residue uses 8 bytes, so one tower needs 512 KiB. Other towers use different primes, but the same array length.

16stages · 32768 butterflies each
524,288butterflies · two kernel launches

Imagine the same array as 256 rows × 256 columns. This is an index view; the stored array stays flat.

global_index = row × 256 + column

Rows and columns both start at 0. Multiplying the row number by 256 skips complete rows; adding the column number selects a slot inside the row. These are element indices, not byte offsets.

Read the memory access map

In pass 1, adjacent loading threads access global addresses 2048 bytes apart (256 × 8 bytes), but write adjacent 8-byte entries in shared memory. The scatter reverses this mapping. In pass 2, adjacent threads read and write adjacent 8-byte global entries. Each block loads once, reuses shared memory across all its stages, and stores once.

Two reads and two writes of the value array give a logical minimum of 4 × N × 8 bytes per forward transform: 2 MiB at N=65536, excluding twiddle/modulus reads and host transfers. This is requested array traffic, not measured DRAM traffic. Strided accesses, caches, registers, and occupancy need real-GPU profiling; 128 active butterfly threads out of 256 is not a hardware occupancy measurement.

Source map: CUDA kernels and launchers define the grid and gather/scatter; the shared stage helper maps threads to pairs and applies the twiddle. Each stage touches every position once.

04 · D2

Why these inputs and twiddles?

The default CUDA path now uses the OpenFHE-style one-multiply butterfly. The column and row passes still assign the same pairs to threads. What changed is how each pair gets its twiddle.

1. Read two slots, then write two results

U is the first slot of the pair in the full tower array. d is the distance in slots at this stage, so its partner is V = U + d. The old values at U and V are a and b, respectively.

\[\begin{aligned} t&=\zeta b,\\ x&=a+t,\\ y&=a-t. \end{aligned}\]

ζ (zeta) is the group's twiddle multiplier. Compute the temporary product t once, then write x at U and y at V. Both writes use the same old a. All value arithmetic is modulo q; the slot indices are ordinary integers.

2. Turn a slot index into a twiddle

One butterfly group contains two halves of d slots each, so the group width is 2d. The two halves are paired offset by offset.

\[\begin{aligned} m&=N/(2d),\\ g&=\lfloor U/(2d)\rfloor,\\ k&=m+g. \end{aligned}\]

m counts the groups at this stage. N/d would count half-groups; divide by 2 to count whole groups. g is the zero-based group containing U: the floor brackets round down, so every slot in the same width-2d group gives the same g. k is the table index; this stage uses entries m through 2m−1.

\[ e=\operatorname{rev}_{\log_2 N}(k),\qquad \zeta=T[k]=\psi^e. \]

T is the forward twiddle table. ψ (psi) is the tower's primitive 2N-th root modulo q: its powers first return to 1 at exponent 2N. e is an exponent, not a slot or table index. The notation \(\operatorname{rev}_{\log_2 N}\) means reverse exactly \(\log_2 N\) binary digits, including leading zeros (16 digits here). This reverses the bits of k at table setup, not the coefficient array during the butterfly.

Example: with N=65,536, d=256 and U=2,563, the group width is 512, m=128 and g=5 because 2,563 is between slots 2,560 and 3,071. Thus k=133, whose 16-bit reversal is 41,216. The pair is (2,563, 2,819), and it uses \(T[133]=\psi^{41216}\).

Why one twiddle is enough: view each group as a polynomial split into a low half \(A(X)\) and a high half \(X^d B(X)\). Its two child groups correspond to \(X^d=\zeta\) and \(X^d=-\zeta\). Substituting gives \(A+\zeta B\) and \(A-\zeta B\): each pair shares the same product \(\zeta b\). At the first split, \(\zeta=\psi^{N/2}\), so \(\zeta^2=-1\), as required by \(X^N+1\).

The bit-reversed table stores the factor for each group in advance. There is no separate input twist pass and no multiply on the difference output. This follows the OpenFHE butterfly and group selection, not its CPU reduction routine.

Find the pair in a column

r is the column number. δ (delta) is the pair distance in shared-memory slots, \(d/256\), because each adjacent entry in a column is 256 slots apart in the tower array. p is the pair number in that column, equal to the active thread's index here. Dividing p by δ and rounding down gives g; the remainder j is the pair offset within that local group.

\[\begin{aligned} u_{\mathrm{local}}&=2\delta g+j,\\ U&=256u_{\mathrm{local}}+r,\\ V&=U+d. \end{aligned}\]

The first line finds the upper shared-memory slot. The second maps it back to a full-array slot. Expanding gives \(U=2dg+(256j+r)\); the last term is smaller than d, so the column's local group number is also the global group number. Changing the column changes the addresses, not the twiddle for that group.

05 · D3

Undo the forward butterfly

The inverse visits the same pairs in reverse stage order. It selects the reciprocal from the inverse table at the same index m+g. For forward outputs x=a+ζb and y=a−ζb, the inverse butterfly produces:

\[\begin{aligned} x+y&=2a,\\ (x-y)\zeta^{-1}&=2b. \end{aligned}\]

Adding x and y cancels the two terms involving b. Subtracting gives twice ζb; multiplying by ζ⁻¹, the modular reciprocal of ζ, cancels ζ because their product is 1 modulo q.

Each of the \(\log_2 N\) stages contributes a factor of two, for a total factor of N. The final kernel multiplies by N⁻¹, the modular reciprocal of N for this tower, to cancel it. Forward runs columns then rows; inverse runs rows then columns then scaling. The inverse consumes the forward transform's bit-reversed evaluation order directly.

The schedule simulator shares the CUDA stage helpers and checks forward arrays, independent inverse arrays and products against the CPU reference. With OpenFHE enabled, it also compares forward and independent inverse arrays directly with OpenFHE. These are host checks, not GPU measurements.

06 · D4

Why two passes equal the full transform

The column proof handles far stages. The remaining kernels—forward_contiguous_tile_kernel and inverse_contiguous_tile_kernel—assign one contiguous tile to each block. For our target sizes, tile length L is 256; for smaller transforms it is min(256,N).

1. Map a row thread to the CPU pair

R is the row block number, L is its tile length, and p is the pair index (threadIdx.x for active threads here). The rows are contiguous, so the local pair distance is the same d as in the full tower.

\[\begin{aligned} g_{\rm local}&=\lfloor p/d\rfloor,\\ j&=p\bmod d. \end{aligned}\]

The quotient selects the group inside this tile; the remainder selects the pair inside that group. Here “mod d” finds an index remainder, not a residue modulo the tower prime q.

\[\begin{aligned} U&=LR+2d\,g_{\rm local}+j,\\ V&=U+d,\\ g&=LR/(2d)+g_{\rm local}. \end{aligned}\]

LR is the start slot of the tile; \(2d\,g_{\rm local}\) skips complete groups within it. Because 2d divides L, \(LR/(2d)\) is the number of complete groups before the tile. Adding the local group gives the global g used in \(T[m+g]\). For example, row 3 starts at 768; at d=128 it starts at global group 3, not group 0. A row is not an independent 256-point NTT.

3. Account for every stage exactly once

The forward distances are the powers of two from N/2 down to 1, measured in full-array slots. For N=65,536 they split at 256:

\[\begin{aligned}\text{Far: }&d=32768,16384,\ldots,256,\\\text{Near: }&d=128,64,\ldots,1.\end{aligned}\]

Forward runs far distances descending, then near distances descending. Inverse reverses both passes and scales by the inverse of 65536. For other supported N≥512, far distances begin at N/2.

There is no missing distance between 128 and 256: no power of two lies between them. Neither set overlaps the other. The far count is log₂N − 8; the near count is 8. Each stage has exactly N/2 disjoint butterflies, so the full count is (N/2) × log₂N per direction. Scaling is not an additional butterfly stage.

4. Why block-local stage fusion is safe

During all far stages, every dependency stays inside the same column; during all near stages, every dependency stays inside the same tile. A block may therefore finish all its stages before another block finishes its first: those blocks do not consume each other's intermediate values within that pass. This reorders independent operations without changing the CPU result.

Loading thread tid copies values[L*R + tid] into shared[tid]. Here tid is an index, not the butterfly product t. All threads reach the load barrier and every stage barrier. Threads 0…127 compute butterflies at L=256, while all 256 threads participate in loading, storing, and synchronization. The block stores its tile once after the last stage.

Between passes, scatter must finish before the next gather. Same-stream kernel order provides that boundary. Gather/scatter changes block ownership; it does not transpose the stored array or perform another transform.

08

What keeps the work ordered?

Inside a block

All 256 threads reach __syncthreads() after loading and after each stage—even threads without a butterfly. This barrier synchronizes only that block.

Between the passes

The kernels use the same CUDA stream, so pass 2 starts after pass 1 finishes. Blocks within a pass are independent; SM scheduling does not guarantee they all execute simultaneously.

For CKKS with multiple RNS primes, repeat this arrangement per limb. Storage is limb-major: values[limb × N + index]. The zero-based limb skips whole towers; index is the slot inside that tower. blockIdx.y selects the limb, and blockIdx.x selects the column or row for the current pass.

The mental model: a block owns a data subset; a thread computes a butterfly within it at each stage. Next, follow the constructor, buffers, and host/device dataflow (D5).
