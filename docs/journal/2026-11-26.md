# Apply Hybrid key-switch contributions transactionally

## Outcome

Added an explicit ciphertext wrapper for the resident Hybrid core. It
handles two-component and three-component CKKS ciphertexts.

## Reasoning

Pinned OpenFHE switches the last component. Its B contribution is added
to the first component in both cases. The A contribution replaces the
second component when there are two inputs and is added to the second
component when there are three inputs. The result has two evaluation
components in either case.

## Changes

[`hybrid_key_switch_in_place`](../../include/ntt/openfhe_hybrid_adapter.hpp)
checks that the ciphertext and key share an OpenFHE context and validates
the leading components before creating a resident session. After receiving
both contributions, it converts and adds on private copies. A single
`SetElements` move commits the two outputs and preserves ciphertext metadata.

## Verification

On the Mac, the two- and three-component wrappers matched pinned OpenFHE
at N=65,536 with four active Q towers. Malformed leading towers were
rejected before submission. Injected late session failure left all three
original components and metadata intact.

With actual CKKS ciphertexts, switching to a new key and relinearizing an
encrypted square both matched the pinned ciphertext residues exactly.
Decryption recovered all four slots within `1e-6`. The native fixture
passed C++ syntax checking. All 34 CPU/OpenFHE checks, 33 documentation
tests and site link validation passed.

## Select relinearization keys automatically

The opt-in adapter now reads the ciphertext key tag and looks up the
OpenFHE multiplication-key vector. It switches `c2`, `c3` and any later
components with their corresponding keys, adds their B and A contributions
to private copies of `c0` and `c1`, and commits the two results together.
A coefficient-form input is converted with OpenFHE before it reaches the
resident core. The adapter opens one session per switched component.

The host fixture uses an encrypted square and cube at N=65,536. Their
relinearized ciphertext residues matched pinned OpenFHE exactly and their
four decoded slots agreed with the expected values within `1e-6`. An
injected cleanup failure on the second component left all input components
unchanged. A missing key tag was rejected before opening a session.

Actual CUDA execution stays queued for the next rental. The next offline
deliverable is an opt-in rotation adapter with exact OpenFHE comparisons
and decrypted-slot checks.

## Rotate CKKS ciphertexts through the resident Hybrid graph

The opt-in rotation adapter selects the evaluation key by ciphertext key tag
and automorphism index. After digit decomposition and the QP multiply-accumulate,
the resident rotation operation adds `P*c0` to the B channel's Q towers and
permutes both channels in bit-reversed evaluation order. ModDown runs on both
permuted outputs before the two result downloads. The same gather and modular
arithmetic run in the host test transport and the prepared CUDA kernel.

At N=65,536, one-slot left and right rotations matched pinned OpenFHE residue
for residue at five and three active Q towers. All eight decoded slots in
each case agreed within `1e-6`. The output matched OpenFHE's ciphertext
metadata. A missing key was rejected before session creation, and an injected
cleanup failure left the input unchanged. All 34 CPU/OpenFHE tests passed.

The next rental will run these fixtures with the CUDA transport. The next
offline deliverable is a reusable rotation digit decomposition so multiple
rotations of one ciphertext can share that work.

## Reuse the Hybrid digits across a rotation batch

`hybrid_rotate_many` uploads the two ciphertext components once and keeps
one digit decomposition for every nonzero shift in the batch. Each shift
uses its own rotation key. Outputs follow request order, and zero shifts
return independent clones without using a key. The adapter checks all key
entries before opening the session and returns the results together after
the session closes. This keeps digit reuse bound to one ciphertext and
one call.

At N=65,536, the batch `[1, 0, -1]` matched OpenFHE's
`EvalFastRotation` residue for residue with five and three active Q
towers. All eight decoded slots in each result were within `1e-6`. Compared
with two independent rotations, the host transport executed 75 instead of
98 queued operations with five active towers and 56 instead of 66 with
three. These counts describe the host test transport. GPU latency remains
unmeasured.

A missing key for the second shift was rejected before session creation.
An injected cleanup failure returned no batch results and left the original
ciphertext unchanged. The native correctness fixture is queued for the next
rental. Prepare paired single-rotation and hoisted timing cases offline so
the same rental can measure both.

## Prepare the paired CKKS rotation benchmark

The host fixture now exports OpenFHE test ciphertexts, rotation evaluation
keys, and expected outputs for four signed shifts at N=65,536. The paired
runner reads those fixed inputs and compares four individual adapter calls
with one hoisted call, alternating which path runs first. Every output is
checked against its saved OpenFHE reference outside the timed interval.

The Mac generated the fixture and replayed two measured pairs each at five
and three active Q towers. All comparisons passed, and the records identify
the backend as host simulation. The rental collector accepts CUDA records
and retains both raw timings and median paired ratios. No GPU timing was
collected. Use the prepared fixture with the next rental batch to measure
the native end-to-end effect.
