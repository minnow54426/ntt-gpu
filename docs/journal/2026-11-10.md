# Standardize the polynomial workload at 65536

## Outcome

The project workload is now N=65536. The work-distribution lesson has one
fixed size, with 256 rows and columns, 16 stages, 524,288 butterflies, and
512 KiB per limb. Both passes launch 256 blocks per limb and use 2 KiB
of shared memory per block. Requested value-array traffic is 2 MiB per forward.

## Reasoning

The user requested removal of the 4096 polynomial and consistent 65536 examples
across HTML and implementations. Small teaching examples and the N=64/1024
correctness fixtures remain: the latter exercise boundary schedules and keep
the independent quadratic Python oracle and schoolbook product practical.
The general transform APIs still accept power-of-two lengths.
Historical notebook observations and cited research ranges remain historical.

## Changes

- Renamed the [work-distribution lesson](../ntt-65536-work-distribution.html),
  updated links and navigation, removed the size selector and comparison column,
  and corrected the memory, launch, and column-proof counts.
- Aligned the butterfly and GPU explainers, site shell, current project scope,
  benchmark plan, and integration plan to N=65536.
- Removed the 4096 CTest fixture. CUDA comparisons and verification now use the
  65536 fixture. The column mapping and optional OpenFHE compatibility gates
  target 65536. Vector generation defaults to 65536; CMake explicitly requests
  1024 for the quadratic oracle.
- CUDA CLI and AutoDL benchmarks default to exponent 16 only. Explicit benchmark
  arguments can still explore other lengths.

## Open questions

Native CUDA and OpenFHE checks depend on their respective toolkit and library.
CPU simulation does not establish GPU launch or synchronization correctness.
