01

CPU and GPU favor different work

A CPU is good at a few complicated tasks. A GPU is good at many copies of the same small task.

A GPU schedules groups of 32 threads called warps. Threads in a warp normally execute the same instruction on different data; different warps can make progress independently. Branch divergence can reduce efficiency within a warp.

At each NTT stage, disjoint pairs use the same butterfly formula. Assigning these pairs to threads exposes parallel work without changing the result.

03

One stage has independent pairs

A stage contains N/2 disjoint butterfly pairs. At N=16, eight pairs can run independently; the next stage must wait for their results.

The example follows all four N=16 stages. The first two fit inside strided columns; the last two fit inside contiguous rows.

Earlier 8-point pairing animation
one stage at N = 8 · click a stage
Every element belongs to exactly one pair per stage — the four butterflies share nothing. Four cooks, zero talking, any order. The fourth button is pass 1 of the real port in miniature (chapter 4).

Butterflies in one stage write disjoint positions, so their execution order does not affect the result. Synchronize before the next stage reads those positions.

A distance-d butterfly stays inside a group of 2d values. This lets one block keep several stages local, provided every dependency stays in its group.

CPU simulation checks the shared index and arithmetic logic. Native CUDA tests must separately check device compilation, barriers and runtime behavior.

04

Split the NTT into two passes

A full N=65536 tower needs 512 KiB, which exceeds the shared-memory capacity available to one block. Split it into smaller groups:

where "1.5 MB" comes from · why the data can't sit on one counter
1 value (one coefficient, one limb)   = 64 bits  = 8 bytes
one limb   = 2¹⁶ values × 8 bytes      = 524,288 B = 512 KB
this repo  = 3 limbs  × 512 KB         = 1,536 KB ≈ 1.5 MB
real FHE   = ~40 limbs × 512 KB        ≈ 20 MB  = 427× a block's whole 48 KB counter
More limbs ≠ harder: each limb is one independent column of the grid (the y address) doing the identical dance — real coefficients are thousands of bits, kept as ~40 machine-word residues, one transform each.

The two-pass design follows from four choices:

①

How the CPU does it — and where it hurts

The CPU reference visits stages and pairs serially. At N=65536, each tower needs 32,768 butterflies per stage and 524,288 in total. The GPU assigns independent pairs to threads; actual speed depends on arithmetic, memory and scheduling costs.

②

First GPU idea: every pair on a cook, everything from VRAM

A simple GPU port could launch one kernel per stage and load/store the whole array each time. That repeats global-memory traffic across all 16 stages. Shared-memory staging reduces those repeated loads and stores.

③

The hardware rule that shapes the fix — and the one choice we get to make

Shared memory belongs to one block. Several stages can run there if all their dependencies fit inside that block's data. This implementation chooses 256 values per group:

counter budget:   48 KB ÷ 8 bytes per value = up to 6,144 values per group
choose:           256 values  (= 2 KB of the 48) — and 65,536 = 256 × 256

A power-of-two group contains complete butterfly groups. At N=65536, 256 × 256 gives a symmetric row/column split. Each block requests 2 KiB; registers and hardware limits also determine how many blocks can run together.

④

That number is the pair distance d

View the array as a 256×256 grid. Distances of 256 or more preserve the column index, so columns own the far stages. Distances 128 or less stay within a row, so rows own the near stages. These two sets cover all 16 stages.

Stated cleanly, the four steps compress into one rule — the one structural idea of this port:

the two-pass split · groups of 256, twice
PASS 1 — the strided groups  (d = 32,768 … 256)
→  256 groups {r, r+256, …} each gather to a counter, run 8 stages, scatter

PASS 2 — the contiguous tiles  (d = 128 … 1)
→  256 tiles of 256 each gather, run 8 stages, scatter

Both passes run the same butterflies as the CPU reference. Pass 1 handles far pairs; pass 2 handles near pairs. This is four logical value movements, but pass 1 currently uses strided, uncoalesced addresses, so the hardware may issue many more memory transactions.

05

Keep a group in shared memory

A block loads one group from global memory, runs its stages in shared memory, then stores the group back:

one block, one group · the kernel's whole life
① 256 cooks gather 256 values (1 each)  ·  ② roll call — values land on the counter  ·  ③ eight butterfly stages, barrier between  ·  ④ carry the results back
Naive code reads and writes VRAM at every stage. The two-pass design loads and stores each group once per pass. That reduces logical traffic, but pass 1 still needs a coalesced transpose or Four-Step layout to make those accesses efficient.

A 256-value group uses 2 KB of shared memory per limb, leaving room for several blocks to reside on an SM. Actual occupancy on the RTX 5090 must be measured after register use and launch limits are known.

The same trick, taken twice

The same staging pattern is used twice: once for strided columns and once for contiguous rows.

one forward at N = 65,536 · two passes, four truck trips

Forward runs columns then rows. Inverse runs rows then columns and finishes with normalization. At N=65536 this means two forward launches and three inverse launches.

06

Map the design to code

For the current arithmetic and a worked CUDA table lookup, see Why these inputs and twiddles?.

The shared stage helper assigns disjoint pairs to threads. Here is the forward arithmetic with names shortened. A window maps local position u to global position origin + stride × u.

for (p = threadIdx.x; p < window_length / 2; p += blockDim.x) {
  u = p + (p / local_distance) * local_distance;
  v = u + local_distance;
  d = local_distance * stride;
  group = (origin + stride * u) / (2 * d);
  zeta = table[N / (2 * d) + group];
  a = shared[u];
  t = mul_mod(shared[v], zeta, q);
  shared[u] = add_mod(a, t, q);
  shared[v] = sub_mod(a, t, q);
}

Second, a column-pass block gathers its strided group, calls the shared stage helper and scatters results. The current kernel keeps this mapping in forward_strided_group_kernel:

__global__ void forward_strided_group_kernel(uint64_t* a, const uint64_t* pp, const uint64_t* q,
                               uint64_t n, uint32_t sub) {
  const uint64_t limb_q = q[blockIdx.y];
  const uint64_t* table = pp + (uint64_t)blockIdx.y * (n + 1);
  extern __shared__ uint64_t smem[];                          // the counter
  const uint64_t r = blockIdx.x;                                // x = which strided group
  uint64_t* al = a + (uint64_t)blockIdx.y * n;               // y = which limb
  for (uint32_t t = threadIdx.x; t < sub; t += blockDim.x)  // ① gather: value r+256t,
    smem[t] = al[r + (uint64_t(t) << 8)];              //    one per cook
  __syncthreads();                                            // ② roll call
  for (uint64_t delta = sub / 2; delta >= 1; delta >>= 1) {  // ③ the 8 far stages,
    transform_stage<false, 256>(smem, sub, delta, n, table, limb_q, threadIdx.x, blockDim.x, r);
    __syncthreads();                                          //    barrier each
  }
  for (uint32_t t = threadIdx.x; t < sub; t += blockDim.x)  // ④ scatter back strided
    al[r + (uint64_t(t) << 8)] = smem[t];
}

The pass-2 kernel (forward_contiguous_tile_kernel) is the same shape with a contiguous gather — it is this kernel with r + (t<<8) replaced by base + t, running the near stages with transform_stage<false, 1> and the tile’s global starting index.

Third, the launch grid identifies independent groups and prime towers. RNS stores one polynomial modulo several primes; each prime's array is called a limb or tower. The grid's y coordinate selects that tower:

// one forward = TWO launches (grid = x × limbs):
forward_strided_group_kernel<<<dim3(256, num_limbs), T, sub * sizeof(uint64_t)>>>(buf, d_pp, d_q, n, sub);
forward_contiguous_tile_kernel<<<dim3(n/256, num_limbs), T, 256 * sizeof(uint64_t)>>>(buf, d_pp, d_q, n, 256);
// pass 1: block (x=r, y=k) = strided group r of limb k — owns {r, r+256, …}
// pass 2: block (x=q, y=k) = contiguous tile q of limb k — owns 256q … 256q+255

Three limbs produce 768 blocks per pass. The y grid coordinate batches limbs in one launch; hardware resource limits determine how many blocks run at once.

There are three synchronization boundaries:

⇄

Between the two passes: the mix is pure data movement

Pass 2 reads pass 1's results. Their same-stream kernel order ensures pass 1 completes first. The scatter/gather changes which block owns each group; it adds no arithmetic transform.

⇄

Between stages inside a pass: the barrier, because partners swap

Within a pass, a stage can read values written by other threads in the previous stage. Every thread reaches __syncthreads() before the next stage starts.

∅

Between blocks: silence — and that is the design

Within one pass, blocks have disjoint groups and no cross-block dependencies. Each block can finish its eight stages independently. With three towers, a pass launches 768 blocks; they need not run simultaneously.

07

Synchronize between stages

Two barrier rules matter:

the roll call rule · why barriers sit between stages
a block is exactly as fast as its slowest thread — so keep everyone's work the same shape

Rule 1: the barrier is all-or-nothing

Every thread in a block must reach the same __syncthreads(). A barrier in a branch taken by only some threads is invalid and can hang the kernel. Here barriers sit outside the pair loop.

Rule 2: idle cooks still attend roll call

A small N=64 tile has only 32 butterfly pairs but still launches 256 threads. Threads without a pair skip the arithmetic loop, then reach the barrier normally. Small fixtures check this boundary.

09

Current baseline and next optimizations

The CPU simulator checks shared stage logic, while native tests check actual CUDA results and execution. The current modular multiply uses a wide product followed by remainder. Its device instruction cost needs profiling; it is not one native 128-bit divide instruction.

The temporary Ada results establish the tested baseline. Candidate improvements include division-free Shoup/Barrett arithmetic, coalesced loads and more register work. Test and measure each change separately.

RTX 5090 validation remains pending. The newer resident runtime also needs its own native lifetime, failure and sanitizer checks.

Recap

A thread computes pairs; a block owns a group. Shared memory reuses that group across stages. Columns handle far pairs, rows handle near pairs, and barriers preserve dependencies. Next, use the N=65536 explorer to trace a specific block and thread.
